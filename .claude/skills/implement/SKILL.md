# 承認済みプランを実装する

`$ARGUMENTS` がプランのパス、または機能名です。

## 0. 前提を確認する

1. `docs/plans/<機能>.md` を読む
2. **ステータスが `承認済み` または `実装中` であることを確認する。**
   `提案中` のままなら実装に入らず、`/plan-feature` の承認手順に戻る
3. ステータスを `実装中` に更新する

## 1. 実装する

プランの「実装ステップ」を順に進めます。

- **プランのスコープ外に手を出さない。** 途中で「ついでに直したい」ものを見つけたら、
  直さずにメモしておき、最後に報告する
- **純粋ロジックを先に書き、テストを添えてから UI に取りかかる。**
  SRS のステージ計算、誤答選択肢の生成、樹のレイアウト選択などは
  React から切り離してテストする(`docs/architecture.md`)
- プランと実装がずれてきたら、黙って進めずプランを更新して合意を取り直す

## 2. 自動チェックと自己修正

編集のたびに `PostToolUse` フックが prettier + eslint --fix を掛けています。
ターンを終えようとすると `Stop` フックが `pnpm run check` を自動実行します。

`pnpm run check` の内訳:

| ステップ | 見るもの |
|---|---|
| `tsc --noEmit` | 型 |
| `eslint .` | 規約 |
| `jest` | テスト |
| `validate-content.ts` | コンテンツデータの不変条件 |

**落ちたら、エラーを読んで直してください。** ここで以下をやってはいけません。

- テストを削除する / `it.skip` にする
- `@ts-ignore` `eslint-disable` で黙らせる
- 検証スクリプトのルールを緩める

これらはチェックを通すのではなく**チェックを壊す**行為です。
どうしてもルール側が間違っていると考えるなら、勝手に変えず開発者に相談してください。

自己修正は **最大3周** で自動的に打ち切られます。打ち切られたら、
未解決の項目を隠さずそのまま報告してください。

## 3. レビュー

`pnpm run check` が通ったら `reviewer` サブエージェントを呼びます。

渡すプロンプトに含めるもの:

- プランのパス
- 何を実装したかの要約
- 「受け入れ条件を1つずつ検証すること」

`reviewer` が「要修正」を返したら、指摘を直してから 2. に戻ります。
**指摘に納得できない場合は、黙って無視せず開発者に判断を仰いでください。**

`src/content/` を触ったなら `content-auditor` も呼びます。

## 4. 完了

1. プランのステータスを `完了` にする
2. 開発者に報告する。含めるもの:
   - 実装したもの
   - `pnpm run check` の結果
   - reviewer の判定
   - **未解決のまま残したこと**(あれば必ず書く。無いなら「なし」と書く)
   - 途中で見つけた「ついでに直したいもの」のメモ
3. コミットは開発者に指示されたときだけ行う

## 報告の姿勢

通っていないものを「通った」と言わないでください。
3周しても直らなかったエラーは、そのまま「3回試したが未解決」と書いてください。
