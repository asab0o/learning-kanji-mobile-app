# コンテンツ仕様

`src/content/` に置く会話文・漢字データの契約。
このアプリの中核資産であり、ここが壊れると学習体験そのものが成立しない。

**方針の根拠は `docs/content-decisions.md`**(会話文 決定事項一覧)。
この仕様はそれをデータの契約に落としたもの。両者が食い違ったら決定事項が正。

型定義は `src/content/types.ts`、検証ルールは `src/content/validate.ts`。

## 規模

| 章     | テーマ       | 総文数 | 新出字 | 第2段階の回 | 課金     |
| ------ | ------------ | ------ | ------ | ----------- | -------- |
| 第1章  | 家の中       | 10     | 10     | 0           | **無料** |
| 第2章  | 一日の暮らし | 15     | 14     | 1           | 有料     |
| 第3章  | 外に出る     | 16     | 13     | 3           | 有料     |
| 第4章  | 学びと世界   | 17     | 13     | 4           | 有料     |
| **計** |              | **58** | **50** | **8**       |          |

実データは `docs/会話文集.md`(v0.2)。

## 未習漢字は使ってよい

**これが最も誤解されやすい点。** 決定事項 4章の通り、会話文には未習漢字を出してよい。

> ふりがな＋英訳があるため読める。既習だけで縛ると不自然な文しか書けなくなる

「読めない字があっても文の意味は取れる」という体験そのものが、漢字への恐怖を下げる
というアプリの目的に効いている。実際 `docs/会話文集.md` では 星・旅・今 などが
自由に使われ、対象50字のうち 花・川・本・新 は導入前の回にも登場する。

**したがって未習漢字は検証しない。** 代わりに `pnpm run validate:content` が
密度を章別に集計して出す。

```
未習漢字の密度(許容されているが、なるべく少ないほうがよい)
  第1章 家の中(無料)    8/10 文  延べ 21 字  1文あたり 2.1
  ...
  あとで習う字を先に使用: 花(#23→#36) 川(#31→#33)
```

第1章を明示しているのは、**無料範囲であり離脱が最も起きる場所**だから。
ここで未習が多すぎると「読めない字だらけ」に見え、新出1字がその中に埋もれる。
数値に合否はつけない。目視で判断する材料として毎回出す。

未習を使わないのは次の2箇所だけ。

1. **第2段階の演出をする漢字の周辺** — 「読みが変わった」ことに集中させたいため
2. **推測クイズの出題** — 既習漢字から推測させるのが目的なので定義上ゆずれない

## 行データの形(ふりがな)

**1行のふりがなは「ひらがな全文の文字列」ではなく、セグメントの配列で持つ。**
根拠は `docs/plans/line-segments.md`。

```ts
{
  speaker: 'grandma',
  japanese: 'たくさん歩きましたね。',
  segments: [
    { text: 'たくさん' },
    { text: '歩', reading: 'ある' },
    { text: 'きましたね。' },
  ],
  romaji: 'Takusan arukimashita ne.',
  english: "We've walked a lot.",
}
```

平坦なひらがな全文にしないのは、そこから「`ある` が `歩` の読み」であることを
機械的に復元できないため(形態素解析が要る)。画面(`FuriganaText`)は漢字の上に
その読みだけを載せるので、対応関係がデータに要る。

### 書き方

- **`reading` は漢字を含むセグメントにだけ付ける。** かなだけのセグメントには付けない
- **`reading` はひらがな(と長音符)のみ。** カタカナ・漢字を混ぜない
- **`segments` の `text` を連結すると `japanese` と一致すること。** ここは error で機械検証する
- **新出漢字はできるだけ単独のセグメントに分ける。** ハイライトはセグメント単位なので、
  `{ text: '今日', reading: 'きょう' }` のように他の漢字と同居すると、その回の1字だけを
  光らせられない(warning)
- **1セグメントは10字以内を目安にする。** 折り返しはセグメント境界でしか起きないため、
  長すぎると吹き出しからはみ出す(warning)

### `focus` は持たない

「いまどの字を光らせるか」はデータに入れない。要件定義書 4.6 のとおり、同じ行でも
出会った瞬間は新出漢字を、第2段階の演出では読みが変わる字を光らせるので、対象が場面で変わる。
付けるのは画面側の `toFuriganaSegments()`(`src/features/reading/segments.ts`)。

## ローマ字の書き方

**ローマ字は手で書かず、`pnpm run romaji` が出した下書きを直して貼る。**
規則を1箇所(`src/content/romaji.ts`)に集め、145行分の表記ゆれを防ぐため。

### 手順

1. `japanese` / `segments` / `english` を書く。**`romaji: ''` のままにしておく**
2. `pnpm run romaji` で未記入の行の下書きを見る
3. **下書きは全行を目で見て直す。** `確認` 印はその中でも特に危ないものを指すだけで、
   **印が無い行にも直しは要る**。印が見るのは `は`/`へ` と固有名詞だけで、
   `が`/`に`/`の`/`も`/`で` の語境界には立たない
4. `romaji` に貼る
5. `pnpm run validate:content` で未記入の警告が消えたことを確認する

漢字の読みは `pnpm run romaji -- --kana <よみ>` で得る。**語単位なので小文字のまま**使う。

### 表記規則

基準は要件定義書 5.2 の「駅名標示など日本の街中の実表記と一致」。
具体的には鉄道掲示基準規程(修正ヘボン式)に従う。

| 項目 | 規則 | 例 |
| --- | --- | --- |
| 基本 | `し shi` / `ち chi` / `つ tsu` / `ふ fu` / `じ ji` / `ぢ ji` / `づ zu` | `つき` → `tsuki` |
| 拗音 | `しゃ sha` / `ちゃ cha` / `じゃ ja` / `きょ kyo` ほか | `しゃしん` → `shashin` |
| 長音 | `おう`/`おお` → `ō`、`うう` → `ū`、`ああ` → `ā`、`ええ` → `ē` | `とうきょう` → `tōkyō` / `くう` → `kū` |
| 長音の例外 | **`いい` → `ii`**(JR 飯田橋 = Iidabashi)、**`えい` → `ei`**(JR 京成 = Keisei) | `ちいさい` → `chiisai` / `せんせい` → `sensei` |
| カタカナ長音符 | `ー` は直前の母音のマクロン | `コーヒー` → `kōhī` |
| 撥音 | `n`。**b・m・p の前は `m`**(JR 新橋 = Shimbashi) | `しんぶん` → `shimbun` / `さんぽ` → `sampo` |
| 撥音の切れ目 | 母音・や行の前は**アポストロフィ** | `しんいち` → `shin'ichi` / `きんようび` → `kin'yōbi` |
| 促音 | 次の子音を重ねる。`ch` の前は `t`。語末は落とす | `がっこう` → `gakkō` / `こっち` → `kotchi` |
| 助詞 | `を` は常に `o`。`は`/`へ` は**語として切り出せたときだけ** `wa`/`e` | `この家は` → `kono ie wa` |
| 定型句 | `こんにちは` → `konnichiwa` / `こんばんは` → `kombanwa` / `では` → `dewa` | — |
| 句読点 | `。`→`.` / `、`→`,` / `…`→`...` / `「」`→削除 | — |
| 大文字化 | 行頭と `.` `?` `!` の直後だけ。**固有名詞は機械が判定しない** | `Takusan arukimashita ne.` |

**駅名標の基準から外すのは1点だけ**で、撥音の切れ目をハイフンではなくアポストロフィにしている。
鉄道掲示基準規程のハイフン(`Shin-Ōkubo`)は複合固有名詞の**構成要素を切る**ための表記で、
`きんようび` のような一般語に当てると `kin-yōbi` となり「金」と「曜日」が別語に見える。
学習教材で一般的な修正ヘボン式のアポストロフィを採る。

### この道具の位置づけ

**綴りの辞書引きであって、そのまま貼れる下書きではない。**
第1章10文(26行)で実測したところ、**綴り(`ō` / `shimbun` / `tsu` など)は全行で正しい**一方、
**20行で語の切れ目の手直しが必要**だった(`nekoga` → `neko ga` など)。
表記ゆれを防ぐという本来の目的は果たすが、分かち書きは人がやる前提で使うこと。

下書きが無修正で正しかった例: `Irasshai. Nagai tabi datta nē.`(#1 の1行目)

### 機械には解けないこと

下書きは近似であって正解ではない。次の2つは**必ず人が見る**。

- **`は`/`へ` が助詞かどうか。** `この家は` の `は` と `はじめまして` の `は` を
  区別する情報がデータに無い。切り出せたものだけ `wa`/`e` にし、残りは `確認` 印を出す
- **語の切れ目。** かなだけのセグメントは割らない(`なに` を `na ni` にしないため)ので、
  `さっきも` は `sakkimo` のまま出る。逆に割りすぎることもある

長音はセグメント境界を越えないので、`思(おも)+う` は `omou` になる(`omō` にしない)。
これは `segments` の構造がそのまま効いている箇所。

## 第2段階のデータ構造

第2段階は **1つの語で複数字の読みが同時に変わる**ことがある(時間 = 時＋間 /
大学 = 大＋学 / 外国 = 外＋国)。8回中3回がこれにあたるため、`kanjiIds` は配列。

```ts
reencounters: [{ word: '時間', stage: 2, kanjiIds: ['k-toki', 'k-aida'] }];
```

「とき＋あいだ → じかん」という**語の組み立てが見える**ことが体験の核なので、
片方だけを記録すると「時 は じ になった」という報告に劣化する。

## 機械では検証できないもの → `content-auditor` の担当

- 語彙レベルが N5 初級者に対して難しすぎないか
- キャラの口調(ミア=対おばあちゃんは丁寧語 / **対空はタメ口** / 空=単語だけ)
- 会話が自然な日本語として成立しているか
- 1文が1〜2往復に収まっているか、登場人数が2人と3人で混ざっているか
- 経過時間に依存する内容(「もう秋ですね」等)が入っていないか

最終的な日本語の品質判断は**日本語ネイティブである開発者本人が行う**。
`content-auditor` はその前段の粗探しであり、承認者ではない。

## 追加のしかた

`/add-content` スキルを使う。

1. 対象の章と、追加する漢字/会話文を決める
2. `src/content/` のデータを編集
3. `pnpm run validate:content` で機械チェック
4. `content-auditor` サブエージェントで品質チェック
5. **開発者本人が日本語として最終確認**
