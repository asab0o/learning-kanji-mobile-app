## 3. コンセプト・差別化ポイント

> 種別: **flow** — 凍結。このアプリが存在する理由そのもの。
> 削ると独自性が消える(3.3 の結論)ため、スコープを削るときもここは守る

### 3.1 コアとなる仮説

漢字を単体の記号として先に暗記するのではなく、**意味のある例文という文脈の中で出会う**ことで記憶に残りやすくなる。そして一度その漢字を知っていると、**後から出会う新しい単語や文の意味を推測しやすくなる**(＝トロントの友人が語っていた体験)。

例文→漢字の順番は「定着させるための入り口」、友人の体験は「定着したあとのリターン」であり、この2つはひとつの学習ループの前半・後半にあたる。

### 3.2 既存アプリとの違い

| アプリ | アプローチ | 弱点(このアプリが埋める部分) |
|---|---|---|
| WaniKani | 部首→漢字→熟語を記憶術で積み上げ | 漢字が先、文脈(生きた会話)が後回し |
| Renshuu / Duolingo | 語彙・文法の一部として漢字が通過するだけ | 「漢字が単語をまたいで意味を広げる感覚」を意識させる設計がない |
| Kanji Pict-o-graphix | 漢字の形を意味の絵に変形する参考書 | 静的な参考書止まり。SRSも例文も再登場の仕組みもない |
| **KANJI Memory Hint**(国際交流基金) | 連想イラスト→漢字のアニメーション＋2種のゲーム。トピック別に漢字を提示(Hint1は58字) | **最重要の競合**。イラストで覚える路線は既に高品質で無料提供済み。ただしSRSがなく、関連語は「漢字ことば」で一度にまとめて提示されるだけ。収録数固定で終わりがある |

**差別化ポイント**: 漢字を「意味の核」として捉え、それが品詞をまたいで単語に広がっていく感覚(例: 歩く→散歩→歩道)を、例文・SRS・段階的な再登場を組み合わせて体験させる。

### 3.3 KANJI Memory Hintとの機能別比較(差別化の所在)

イラストで覚えること自体は、公的機関が無料で高品質に提供済みのため**差別化ポイントにならない**。差が出るのは以下の3点。

| 機能 | KANJI Memory Hint | このアプリ |
|---|---|---|
| 導入の仕方 | トピック別の単語リストから | **会話文の中で自然に出会う** |
| 復習の仕組み | ゲームでの繰り返しのみ(間隔反復なし) | **SRSで忘却曲線に沿った最適タイミングで復習** |
| 漢字の再登場 | 「漢字ことば」で関連語を一度にまとめて提示 | **時間差をつけて別の会話シーンに段階的に再登場させ、"気づき"として演出** |
| コンテンツの継続性 | 収録漢字数が固定、終わりがある | 顔なじみキャラ・継続する会話シリーズとして展開可能(サブスク継続理由になる) |

→ **最大の差別化は「段階的再登場」**。ここを削ると本アプリの独自性が消えるため、MVPでの優先度は最上位。

## 4. コア体験・学習ループ

> 種別: **stock** — 現在の体験設計。変更したら `decisions/` に理由を残す

差別化ポイント(漢字が「意味の核」として品詞をまたいで単語に広がっていく感覚)を、**入口・体験・可視化の3層**で表現する。

| 層 | 担当する仕組み | 役割 |
|---|---|---|
| 入口 | 会話文で出会う | 文脈の中で漢字と初対面する |
| 体験 | **推測クイズ「読めるかな?」** | 未習の単語を、既習漢字から推測させる。友人の体験(漢字を覚えると新しい語の意味がわかる)を直接ゲーム化したもの。**面白さの主軸はここに置く** |
| 可視化 | **漢字の樹** | 覚えた漢字を中心に、出会った単語が枝として伸びる(歩→歩く→散歩→歩道)。進捗確認画面を兼ねる |

### 4.1 学習ループ

1. AI生成のオリジナル日常会話文(初級者レベルに調整)を、ふりがな＋英訳つきで提示(ローマ字は設定でON/OFF)
2. まず文全体の意味をつかむ
3. 文中のキーとなる漢字にフォーカス。意味を象徴するイラスト(Kanji Pict-o-graphix的な絵)で覚え方を学ぶ
4. その回で出会った漢字をSRS(間隔反復)で復習。**出題は意味の4択のみで、会話文は再表示しない**(形式は5.1-4)。どの文で出会った字かは記録に残す(理由は ADR-0007)
5. 学んだ漢字が、別の日常シーンの会話文に段階的に再登場する
   - **第1段階**: 同じ単語・同じ読みで、別のシーンに再登場(「見覚えある」感覚を作る)
   - **第2段階**: 別の単語・別の読み方で再登場させ、「同じ漢字だけど読みが変わった」ことを明示的に演出(演出仕様は4.6参照)
6. **推測クイズ**: 未習の単語を提示し、既習漢字から意味を推測させる。答え合わせで種明かし(仕様は4.4参照)
7. **漢字の樹**に成果が蓄積され、単語の広がりが目に見える形になる(仕様は4.5参照)

### 4.2 会話文の設計方針

会話そのもので楽しませようとせず、**会話は「漢字と出会う場」に徹する**。面白さの主軸は推測クイズ(6)が担うため、会話は自然で短ければ十分。

- **ストーリーの連続性は持たせない**。「同じキャラの、別々の日常の一場面」を積み重ねる4コマ漫画的な構成にする
  - 理由: 連続ドラマ形式は前回を覚えていないと楽しめず、途中参加もしづらい。制作負荷も高い
- **キャラには一貫した性格をつける**(例: いつも寝坊する、やたら食べ物の話をする)。ストーリーがなくても性格の一貫性だけで愛着は生まれる
- 1文の長さは1〜2往復に徹する(短ければ飽きる前に終わる)
  - **例外: オチが要る回は2.5往復(5行)まで許容する**(ADR-0005)。振り返し数ではなく1行の短さで負荷を抑える
- シチュエーション(カフェ、駅など)を固定し、「顔なじみ」感を出す

### 4.3 登場キャラクター設定

**舞台設定**: 留学生ミアが、おばあちゃんの家にホームステイしている。飼い猫の空(そら)がいる。

この設定を採用した理由:

- 3人が毎回同じ場所にいる理由が自然に説明でき、会話の不自然さが消える
- ミアが日本語について質問するのが完全に自然になり、**説明を会話の中に埋め込める**(注釈を別枠で出さずに済む)
- 家という舞台で生活語彙が広くカバーできる(食べる・飲む・部屋・朝・夜・出る・入る等)
- 家から出ない縛りはなく、買い物・散歩など外出回も混ぜられる

| | ミア | おばあちゃん | 空(そら) |
|---|---|---|---|
| 立ち位置 | 留学生・ホームステイ中 | 家主・ホストマザー | 家の飼い猫 |
| 役割 | 質問する側(ユーザーの分身) | 説明する側 | 崩す側(会話に緩さを出す) |
| 性格 | 好奇心旺盛、何でも聞く、たまに勘違いする | 世話焼き、天気の話から入る、褒め上手 | 気まぐれ、要求だけ言う、都合が悪いと寝る |
| 口調 | 丁寧語(学習者らしくやや硬い)「これは、どういう意味ですか?」 | やわらかい年配の話し方「あらあら」「〜だねえ」 | 単語だけ、雑「ごはん」「ねむい」「外」 |
| 語彙領域 | 質問・学習系(何・読む・書く・言う・見る) | 生活・天気・食事(食べる・飲む・雨・晴・朝・夜) | 動作・位置(出る・入る・上・下・外・寝る) |

**空の発話ルール**: 要求・状態・存在のみを言い、挨拶や応答はしない。猫がどこまで言葉を解するのかという設定の線引きを曖昧にしないため。

**3人にした理由**: 2人だと会話パターンが1通りで単調になり、4人以上は初級者が覚えきれず「顔なじみ」感が薄れる。3人なら組み合わせが3通りに増える。

**口調を意図的に分けている**: 語尾・文長・語彙が3人とも異なるため、名前を見なくても誰の発話か判別できる。特に猫の空は単語だけの発話が許されるので、**初級者向けの極端に短い文を自然に作れる**。

**語彙領域の分担が学習機能として働く**: 「このキャラが出てきたらこの系統の漢字」という連想が生まれ、記憶のフックが一つ増える。

**猫の名前「空(そら)」の選定理由**:

- 訓読み「そら」として先に覚えさせ、後に「空港(くうこう)」「空気(くうき)」で音読みに出会わせることで、**第2段階(読みが変わる気づき)の教材としてそのまま機能する**
- 「単体の語は訓読み → 熟語で音読みに変わる」という日本語の一般構造と一致し、学習の自然な進み方に沿う
- 毎日登場する猫の名前なので記憶への定着が強い

**キャラのイラストは顔アイコン3枚のみとする**(立ち絵・全身絵は作らない)。

- 会話の吹き出し横に表示し、誰の発話かを一目で分かるようにする。テキストのみより格段に読みやすくなる
- **1キャラ1枚固定**。表情差分・ポーズ違いは作らない(アセットが膨らむため)
- 制作順序は**漢字イラストの画風プロンプトを確定させた後**にキャラアイコンを生成する。逆順だと画風がちぐはぐになる

### 4.4 推測クイズ「読めるかな?」仕様

**出題タイミング: 2箇所で出す(役割を分ける)**

| タイミング | 役割 | 難易度 |
|---|---|---|
| **学習直後** | チュートリアル的役割。「このアプリではこういう推測ができる」という仕組みを教える。初日から体験が成立する | 易しめ |
| **数日後(SRS復習セッション中)** | 本番。記憶から引き出させ、「覚えていた漢字が効いた」という本物の驚きを作る | 難しめ |

出題ロジックは共通で、呼び出すタイミングが違うだけ。片方を実装すればもう片方はスケジューリングの問題になる。

**出題対象の選び方**

既習漢字を含む未習の単語を出す。ただし初期は既習漢字が少なく組める熟語がほぼないため、以下も対象に含める。

- 単漢字の別の読み(「空(そら)」を既習 →「空気」の「空」は?)
- 既習1字＋未習1字の熟語(片方だけ分かれば意味は推測できることが多い)

**出題形式: 意味の4択 ＋ 2段構え**

1. まず漢字だけを見せ、「意味を推測してみて」と考える時間を与える(ボタンを押すまで選択肢を出さない)
2. タップすると4択が現れ、選ぶ
3. 答え合わせで**構成要素の種明かし**を表示(例: 歩=walk + 道=road → sidewalk)

→ **3の種明かしが最重要**。ここで「漢字が意味の核である」ことを毎回体感させる。

**誤答選択肢の作り方**: ランダムではなく、**片方の漢字だけ合っている紛らわしい選択肢**を混ぜる(歩道 → sidewalk / walking speed / roadside)。推測の質が上がる。

**結果はSRSに入れない**。あくまで「ご褒美体験」として、正解しなくても罰がない設計にする。成績管理にすると挑戦する気持ちが削がれるため。

### 4.5 漢字の樹 ビジュアル仕様

40〜60字ぶんの枝を1画面に描くのは破綻するため、**1漢字につき1本の樹**とする。

**構造**

- 漢字一覧(グリッド)から1字をタップ → その漢字の樹が開く
- 中心に漢字1字を大きく配置し、そこから枝が伸びて、出会った単語が葉として付く
- **未出会いの単語は灰色のつぼみとして表示** → 「まだ先がある」という継続動機になる

```
        [空気] ← 灰色のつぼみ(未出会い)
           |
   [空]  ← 中心
    |   \
 [そら]  [空港] ← 出会い済み(色つき)
```

**読み方の区別を色で表現**

- 訓読みの枝 = 緑系 / 音読みの枝 = 青系
- → 樹を見るだけで「この漢字は読みが2系統ある」ことが視覚的に分かり、4.6の演出とも連動する

**実装方針**

- react-native-svgで描画
- 枝の座標は動的計算せず、**単語数ごとのレイアウトパターンを数種類用意して当てはめる**(1〜2語用 / 3〜4語用 / 5語以上用)。動的グラフ描画アルゴリズムはMVPには重すぎる
- 一覧画面では各漢字の「出会った単語数」をバッジ表示

### 4.6 「読みが変わった」ことを見せるUI演出

やりすぎると押し付けがましく、控えめすぎると気づかれない。**3ステップ構成**とする。

**ステップ1: 出会った瞬間**

会話文中の該当漢字をアクセントカラーでハイライトし、小さくバッジ(★など)を付ける。ここは控えめでよい。

**ステップ2: タップで種明かしカード**

ハイライトをタップするとカードがせり上がる。

```
   空
そら  →  くう
[訓読み]   [音読み]
Same kanji, different reading!
The meaning stays: "sky / empty"
```

→ 伝えるべき核心は「**読みは変わるが、意味の核は変わらない**」。差別化ポイントそのものなので、文言はここに集中させる。

**ステップ3: 樹への反映**

カードを閉じると、漢字の樹に新しい枝(青=音読み)が生える短いアニメーション。「学びが蓄積された」実感と4.5の可視化が繋がる。

**演出の頻度制限**: 同じ漢字につき1回だけ。2回目以降はハイライトのみ(バッジなし)。毎回出すとうるさくなる。

### 5.2 表記・表示の仕様

- **ふりがな(ひらがな)を標準表示**とする
- **ローマ字表記は設定でON/OFF切り替え**(デフォルトOFF)。ONの場合、日本語の全文に対して小さく添える
  - 方式は**ヘボン式**(shi, chi, tsu, fu)。駅名標示など日本の街中の実表記と一致し、「身近に感じる」コンセプトと合致するため
    - 長音・撥音・分かち書きなどの詳細な表記規則は `docs/content-spec.md`「ローマ字の書き方」
  - ふりがなとローマ字の2段表示は画面が詰まるため、常時併記はしない
- **音声読み上げは実装しない**(シンプルさ優先。音声生成・品質確認・アプリサイズ増を回避)
- 訳の言語は**英語のみ**(多言語化は翻訳品質の担保コストが大きいため見送り)

### 5.3 テーマ仕様

**MVP は桜1種のみを積む(ADR-0006)。** 設定からの切り替えUIも作らない。
残り2種は v2 以降。トークン層・`user_settings.theme_id` は3種を受けられる形のまま残してあるので、
**足すときに要るのは配色1つと背景画像1枚だけ**で、既存画面の色指定を洗い直す必要はない。

**制約(MVPスコープを守るため)**

- 基本は色とグラデーションで表現する。**テーマごとの背景装飾は1〜2枚まで許容**(例: 桜=舞う花びらのパターン1枚、夜景=ビル群のシルエット1枚)
  - 全画面で同じ装飾を使い回す。画面ごと・シーンごとに違う背景は作らない
  - 合計3〜6枚に収める。これを超えると制作・実装ともスコープが崩れる
- **漢字イラストはテーマ非依存**(50枚を3テーマ分＝150枚は非現実的)。背景透過PNGとし、どのテーマ背景でも使えるようにする
- テーマによってUI部品の形は変えない(色と背景のみが変わる)
- **1種に絞っても、テーマを足せる作りは壊さないこと**(ADR-0006)。具体的には
  `ThemeId` を単一リテラルに固定しない / `themes` の `Record<ThemeId, Theme>` を素の
  オブジェクトに崩さない / `user_settings.theme_id` 列を落とさない /
  `ThemeProvider` の `themeId` プロパティを消さない
- 実装は色定義オブジェクトをContext経由で配る形。工数は半日〜1日程度

**視認性の注意(デザイン依頼時に共有すべき点)**

背景に絵が入ると、その上に載る漢字イラストやテキストの視認性が問題になる。特に「東京の夜景」は濃色のため、charcoal(`#3E3630`)の文字が読めなくなる恐れがある。

- 背景装飾は薄く敷く(opacity 0.1〜0.2程度)、またはコンテンツ部分に半透明カードを重ねる設計にする

**実装上の注意**: 最初から色をハードコードせず、`theme.background` / `theme.text` / `theme.accent` のようにトークン化しておくこと。後付けでテーマを足すと全画面の色指定の洗い直しが発生する。

### 5.4 コンテンツ規模・制作方針

- 会話文: **全58文**(新出漢字50字＋第2段階専用の回8文)。執筆済み、別紙『会話文集.md』参照
  - 1文につき新出漢字1字。第2段階(読みが変わる)の回のみ新出漢字なしの特別回とする
  - 章構成: 第1章「家の中」10文 / 第2章「一日の暮らし」15文 / 第3章「外に出る」16文 / 第4章「学びと世界」17文
  - **第1章(10字)を無料範囲とし、課金の境界と章の切れ目を一致させる**(「1章分まるごと無料で体験 → 続きはサブスク」という導線にするため)
  - 1日3字が上限のため、全50字は約17日で完走する想定(第1章の無料10字は約3〜4日)
  - 登場人数は2人の回と3人の回を混ぜる
- 対象漢字: **40〜60字**(1人でイラスト制作と例文設計を回せる上限)。**MVPは50字で確定**、選定結果は別紙『対象漢字リスト.md』参照
  - 選定方針: JLPT N5範囲を母集団とし(実用性の担保)、**訓読み/音読みの対比が作れる字を最優先で絞り込む**(差別化の核が機能するため)。並び順はホームステイの日常シーンで自然に出る順
  - 訓読みのみで広がりが作れない字(猫・耳・足など)は、N5頻出でも**意図的に除外**する。主機能が空振りするため
  - 品詞バランスは動詞やや多め。動詞は派生で単語が広がりやすく、会話文も成立させやすい
- 1文の長さ: **1〜2往復の会話**(日常会話の空気が出る最小単位)
- 会話文の作り方: **AI生成 → 自分で検品**(日本語ネイティブとしての品質チェックを必ず挟む)
- イラスト: **AI生成 → 手動選別**。画風は「質感のあるフラット/モダン」＋「人・動物を入れる」方式。詳細は別紙『画風プロンプト定義.md』参照
  - まず山/空/歩/**思**の4字でテスト生成し画風を確定させてから、残りをバッチ生成する(抽象語の「思」で破綻しないことが合格ライン)
  - 生成物は背景透過PNG化する(テーマ3種のどの背景でも使えるようにするため)
- イラストは**静止画のみ**(イラスト→漢字のアニメーションはKANJI Memory Hintが高品質で実装済みのため、正面から競合しない)
- キャラアイコン: **顔のみ3枚**(ミア/おばあちゃん/空)。漢字イラストと同じ画風プロンプトで生成する

## 6. 技術要件

> 種別: **stock** — 現在の技術方針。変更したら `decisions/` に理由を残す

### 6.1 プラットフォーム

- **iOSのみ**(iPadOS等は問わない)
- Expo(React Native)+ TypeScriptで実装。既存のReact経験を活用
- **AWSは使用しない**。サーバー・バックエンドを持たない構成(6.3参照)
- **オフライン対応**: 学習部分(会話文・漢字イラスト・SRS復習・推測クイズ・漢字の樹)はすべてローカル完結で、ネット接続なしで利用できる。RevenueCatでの購入時のみ通信が必要(購入後の有料範囲アクセスはオフラインでも可能)
- 想定アプリサイズ: 30〜55MB程度(Expo/RNランタイム20〜40MB＋イラスト5〜10MB＋その他)。音声非採用・イラスト静止画のみ・テーマアセット最小限の判断が軽量化に寄与

### 6.2 主なライブラリ・SDK

- RevenueCat SDK(課金)
- Drizzle ORM(TypeScript製。SQLite/Postgres間でスキーマ定義をほぼ共通化できるため採用)
- react-native-svg(漢字の樹の描画)
- ローカルDB: SQLite(Expo標準)

### 6.3 データ設計方針(将来のクラウド移行を見据えて)

MVPは**ログインなし・ローカル保存のみ**とするが、将来クラウド同期を追加しやすいよう、以下を最初から仕込んでおく。

1. 主キーはUUID(またはULID)。auto incrementは使わない(将来の複数端末データ統合時のID衝突を避けるため)
2. 全テーブルに`created_at` / `updated_at`を持たせる
3. 「コンテンツ」(例文・漢字・イラストなどのマスタデータ、アプリに同梱・同期不要)と「ユーザー状態」(復習履歴・進捗、将来の同期対象)をテーブルレベルで分離する
4. SRSの状態は**イベントログの追記方式**で持つ(現在状態を1レコード上書きする設計にしない → 将来の複数端末同期時に競合解決ロジックが不要になる)

```ts
// review_events(追記のみ。将来の同期対象)
{
  id: uuid,
  kanjiId: string,
  sentenceId: string,
  result: "correct" | "incorrect",
  reviewedAt: timestamp,
}
// kanji_progress は review_events から都度計算するキャッシュとして扱う
```

5. マイグレーションは最初から管理する(drizzle-kit)

### 6.4 リスク回避事項

- 実在の漫画・ニュース記事からのセリフ抽出は著作権リスクがあるため不採用。**会話文はAIによるオリジナル生成**とする

## 7. 収益化要件(RevenueCat)

> 種別: **stock** — 現在の課金仕様。変更したら `decisions/` に理由を残す

- Shipaton参加要件としてRevenueCat SDKの導入・サブスク課金実装が必須
- **プランは月額の単一プランのみ**(課金画面もRevenueCat設定も最小になる。買い切りはサブスク要件を外れる恐れがあるため不採用)
- **無料と有料の境界: 第1章(10文)まで無料、第2章以降はサブスクで解放**(価値を体験させてから課金でき、実装も単純。章の切れ目と一致させることで導線が自然になる)
- **無料トライアルは設定しない**(「第1章まるごと無料」が実質のトライアルとして機能するため二重に用意しない)
- ログインなし運用のため、購入はApple IDに紐づく。「購入の復元」ボタンを実装し、再インストール時も課金状態を復元できるようにする(Apple審査でも必須項目)
- アナリティクスはRevenueCat内蔵の計測のみ利用
- 価格(金額)は未決定(→9章の未決定事項)
