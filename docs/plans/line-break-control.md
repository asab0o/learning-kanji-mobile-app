# プラン: line-break-control

作成日: 2026-09-10
ステータス: 実装中
要件定義書の対応箇所: 5.2 表記・表示の仕様 / 4.6 ステップ1(★の表示)

## 目的

会話文の吹き出しの折り返しを、幅任せではなく**作者が指定した位置**で起こせるようにし、
挙がっている17行の不自然な改行と、閉じ括弧が行頭に落ちる2件(#20 / #30)を直す。

## 先に指摘すること

1. **要件定義書に改行位置の規定は無い。** 5.2 は「ふりがな標準表示 / ローマ字は任意」までで、
   折り返しには触れていない。よって要件との矛盾は無く、これは表示品質の改善として扱う。
   最も近い既存の取り決めは `docs/plans/conversation-screen.md` の受け入れ条件
   「`？` だけが次の行に落ちない」で、今回の禁則処理はこれを一般化したもの。

2. **#30 の修正は `docs/content-spec.md`「演出行の書き方」5 と衝突するため、spec を書き換える。**
   実測に基づく幅の見積り(吹き出し内容幅 = 236 − padding 14×2 − border 1×2 = **206pt**、
   全角1字 = `jaSize` 17.5pt ⇒ **1行に約11.7字**)では、
   `おしいねえ。「水曜日」、` は12字 = 210pt で **206pt に入らない**。
   つまり **`水曜日` を1行目に置いたまま `」、` を1行目に収める解は存在しない**。

   **決定(2026-09-10、開発者):** `おしいねえ。` の後で強制改行し、2行目を `「水曜日」、ここでは` にする。
   演出語は割れず閉じ括弧も行頭に来ない。★が折り返し2行目に来るため、**実装側で上マージンを入れて
   重なりを解消する**(決めどころ 4)。あわせて content-spec の「演出行の書き方」5 を
   「演出語が折り返しで**分断**されないこと」に書き換える。
   (`src/content/CLAUDE.md` の該当文は「機械検証できないので目視する」という主旨が変わらないため触らない)

3. **平文セグメントの分割が必要なのは4件ではなく11件。** 当初想定(借りても/書いて/聞いても/日本のこと)に
   加え、`にも、こういう`(#54)、`しいものは、`(#52)、`がきれいですね。`(#9)、
   `んだねえ。あたしも`(#29)、`は、お`(#41) と、不具合2件(#20 / #30)の
   `はい。……「` `おしいねえ。「` も割る必要がある。実データで確認済み。

4. **件数の内訳。** 開発者の18件は「強制改行17行 + #30 の不具合1行」。#20 を足して**触る行は19**。

5. **「〜で改行」の解釈は『その語の後で切る』に統一した。** `にも、` / `毎日、` / `星が` /
   `年が` は前で切ると助詞が行頭に来るため、後ろで切る以外に読めない。
   **例外は #41 のみ。決定(2026-09-10、開発者): 「今日は、」で切る**(= `お休み` の前)。
   `今日は、` / `お休みなんです。` となり、語が割れない。

## スコープ外

- **`japanese` の文面変更**。1字も触らない
- **`BUBBLE_MAX_WIDTH` / `jaSize` / padding の調整**。実機で合わせた値(conversation-screen.md:205)
- **行末禁則(開き括弧が行末に残るのを自動で防ぐ)。** `」と「` のように前後どちらにも
  くっつきたいセグメントが連鎖し、クラスタが吹き出し幅を超えて**はみ出す**危険がある。

- **吹き出しが1画面に収まらない回への対処。** 既に `ScrollView` で、CTA をスレッド末尾に
  置いている設計と矛盾しない。**縮小や折りたたみはしない**
- **今回挙がっていない41本の折り返し調整。** 全数目視で気になっても直さず、作業録に列挙するだけ
- 会話画面以外への波及。`FuriganaText` の利用箇所は `conversation-view.tsx` の1つだけ(確認済み)

## データモデルの変更

**マイグレーション不要。** `sentence_lines.segments` は JSON 文字列列で
(`mappers.ts` の `toSentenceLineRow` が `JSON.stringify`)、列は増えない。
`isLineSegment` は余分なキーを弾かないので既存 DB も読めるが、
型として明示するためガードに `breakAfter === undefined || typeof breakAfter === 'boolean'` を足す。

`contentFingerprint()` は `stableStringify` で全プロパティを見るため、
`breakAfter` を1つ足した時点で指紋が変わり、**起動時に自動で再シードされる**(想定通り)。

## 決めどころ

### 1. 強制改行は `LineSegment.breakAfter?: boolean` で表す

検討した代替案と却下理由。

- **`Line.segments` を `LineSegment[][]`(行の配列)にする** — 表現としては最も素直だが、
  145行ぶんのデータ書き換えに加え、`checkLineSegments` / `checkReencounterRevealLine` /
  `revealFor()` の `badgeSegmentIndex`(平坦な添字)/ `segmentsToRomajiDraft` /
  `mappers.ts` の型ガードが全て平坦配列前提。締切前に触る範囲としては大きすぎる
- **`Line.breaks?: number[]`(改行する添字)** — セグメントを1つ割るたびに添字がずれ、
  **ずれても機械は気づかない**。フラグはセグメントに同居させるほうが編集に強い
- **`text` にゼロ幅制御文字を混ぜる** — `segments` の連結 = `japanese` の検証が壊れる。却下

`breakAfter` は `segmentsToText` / `segmentsToKana` に影響しない(`text`/`reading` しか見ない)ので、
`checkLineSegments` の連結一致検証はそのまま通る。

### 2. 禁則は「自動」で持つ(データに書かない)

行頭に来てはいけない字で始まるセグメントは、**直前のセグメントと同じ「クラスタ」に入れて
折り返し不可**にする。データ側の指定は要らない。

- 対象文字(最小限): `、。，．・？！…` と閉じ括弧 `）］｝」』】〕》〉` と `ー` と小書きかな
- **連結の上限を8字とする。** 上限が無いと `」と「` のような両側にくっつきたい並びで
  クラスタが伸び、吹き出し幅(約11.7字)を超えて**はみ出す**。上限に当たったら連結しない
  (結果は現状と同じ = 目視で気づける)
- **`breakAfter` は禁則より優先。** 作者が明示した改行を機械が握り潰さない。
  代わりに「`breakAfter` の直後が禁則文字で始まる」データを `checkLineBreaks` が warning で拾う

判定関数を `src/content/segments.ts` に置くのは、`validate.ts`(content 層)と
`line-layout.ts`(features 層)の両方が要るため。レイヤ順 `features → content` に沿う。
content 層が表示都合のルールを持つ前例は既にある(「1セグメント10字以内」)。

### 3. 描画は「幅100%のスペーサ」ではなく行を分けて入れ子にする

> **実装後の記録(2026-09-11): この判断は実機で覆した。** 入れ子にすると、折り返す行が
> 親に**最小幅**(最大クラスタの幅)を報告するため吹き出しが縮み、**指定していない所で
> 折り返し直す**。#14 が `この言葉が、/ 分 / かりません。` となり `分` が1行に孤立した。
> 幅100%のスペーサに差し替えたところ、懸念していた「吹き出しが常に最大幅になる」は起きず
> (パーセント指定は内在幅の計算に入らない)、#14 は `この言葉が、/ 分かりません。` に戻った。
> ★の隙間はスペーサの高さで確保する。以下は当初の判断として残す。

```
View(column)                       ← アクセシビリティのラベルはここ(現状どおり)
└ View(row, flexWrap: 'wrap')      ← breakAfter で区切った1行。中はさらに幅で折り返す
  └ View(row, nowrap)              ← 禁則クラスタ。ここでは絶対に折り返さない
    └ 既存のセグメント箱(読み/本文/下線/★)  ← 中身は無改造
```

- スペーサ案(高さ0・幅100%)だと `width: '100%'` が Yoga の**内在幅の計算**にどう効くかが不確実で、
  吹き出しが常に最大幅に張り付く可能性がある。構造で分ければ挙動が確定する
- **禁則(折り返し不可の連結)はスペーサでは表現できない**。どのみち入れ子の nowrap 行が要る
- `styles.row` に `rowGap` が無いので、行を分けても**行間は現状と一致する**
- 副作用: 強制改行で最長行が短くなると、**吹き出しの幅が今より狭くなる回がある**。
  悪化ではないが見た目は変わるので全数目視で確認する

### 4. ★の重なり(#30 のための最小限の追加)

`toLayoutLines()` の結果は「どの行に `badge` があるか」を JS で知れるので、
**強制改行で作った2行目以降が★を含むときだけ**その行に上マージン
`(badgeSize + 2) * fontScale` を入れる。3行程度の変更。

**自然折り返しの2行目に★が来る場合は従来どおり重なる**(JS から位置が見えない)。
よって「演出語を行頭寄りに置く」という執筆側の心得は残す。

### 5. ブランチは分けない

19行のデータ編集は機械的で、仕組みの変更と切り離すと**58本の全数目視を2回やる**ことになる。
1ブランチ `feat/line-break-control` にまとめ、コミットで分ける。

1. 仕組み(`line-layout.ts` + `furigana.tsx` + `types.ts` + `mappers.ts` + テスト)
2. 禁則だけで直る範囲の確認(データ変更なしでスクショ)
3. データ19行
4. ドキュメント

目視で「指定どおりに切ったら今より悪い」行が出たら、**その行のフラグだけ落として作業録に残す**。
スコープを広げない。
