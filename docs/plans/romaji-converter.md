# プラン: romaji-converter

作成日: 2026-08-28
ステータス: 完了
要件定義書の対応箇所: 5.2(表記・表示の仕様)、5.4(コンテンツ制作方針)、6.2(データ設計)

## 目的

会話文 58 文(約 145 行)と漢字 50 字の読みに付けるヘボン式ローマ字を、**規則を 1 箇所に集めた純粋関数と執筆用 CLI から生成できる**状態にする。145 行を手で書いたときに必ず出る表記ゆれ(`tsu`/`tu`、`Tōkyō`/`Tokyo`、`shimbun`/`shinbun`)を、機械が出した下書きを人が直す形に置き換える。

### 先に指摘すること(要件・既存ドキュメントとの差分)

1. **要件定義書 5.2 は「ヘボン式(shi, chi, tsu, fu)」としか書いていない。**
   長音・撥音・助詞・分かち書き・大文字化は未定義であり、本プランで確定させる。5.2 の根拠は
   「駅名標示など日本の街中の実表記と一致」なので、**判断基準は JR の駅名標(鉄道掲示基準規程)に置く**。
   確定先は `docs/content-spec.md` とし、要件定義書 5.2 には参照 1 行だけを足す(5 章は stock)。

2. **既存データに書かれているローマ字の実例と、駅名標基準は一致している。**
   `src/db/mappers.test.ts` の `'Ohayō gozaimasu.'` / `{ kana: 'くう', romaji: 'kū' }`、
   `src/db/mappers.test.ts` の `'Irasshai.'`、`docs/content-spec.md` の
   `'Takusan arukimashita ne.'` は、いずれも**マクロン長音・分かち書き・文頭大文字**。
   本プランはこれらを仕様として追認する(既存の実例を書き換えない)。

3. **`docs/content-decisions.md` 8 章と `docs/会話文集.md` の未確定事項に、同じ項目が二重にある。**
   `content-decisions.md` は **flow(書き換えない)** なので、line-segments のときと同じく
   **`docs/会話文集.md`(stock)側だけにチェックを入れ**、確定先を参照させる。

### 決める 3 点(結論)

| 論点 | 結論 |
|---|---|
| **いつ動くか** | **執筆時のみ。** CLI が下書きを出し、人が直して `src/content/index.ts` に貼る。`Line.romaji` / `Reading.romaji` は今までどおり**手で書かれたデータが正**。実行時変換はしない |
| **分かち書き** | 前プランの **(a) を基本に、(b) を「下書きの精度を上げるヒューリスティック」として限定採用**。データモデルは変えない((c) の語境界フラグは足さない) |
| **表記仕様** | 鉄道掲示基準規程(修正ヘボン式・長音はマクロン・b/m/p の前は `m`)。ただし撥音の切れ目だけはハイフンでなく**アポストロフィ** |

**執筆時に倒す理由。** `は`/`へ` の助詞判定は文脈依存で機械には解けない(`この家は` の `は` と
`はじめまして` の `は` を区別する情報がデータに無い)。人の手が入らない実行時変換にすると、
この誤りが**そのままユーザーに出続ける**。執筆時なら CLI が下書きと「要確認」印を出し、
日本語ネイティブである開発者が 145 行を 1 度直せば終わる。

**(c) 語境界フラグを採らない理由。** 語境界は執筆者が 145 行分入力しないと埋まらず、その労力は
「ローマ字を直接直す」のとほぼ同じ。しかも語境界は**ローマ字のためだけ**に存在するフィールドで、
表示(折り返し)には無関係なので、`segments` に表示以外の関心を混ぜることになる。

## 実装ステップ

### 1. 表記仕様を確定して `docs/content-spec.md` に書く

**基準**: JR の駅名標は鉄道掲示基準規程に基づく修正ヘボン式で、**長音はマクロン**、
**撥音は b・m・p の前で `m`**(新橋 = `Shimbashi`)。

| 項目 | 規則 | 例 |
|---|---|---|
| 基本 | `し shi` / `ち chi` / `つ tsu` / `ふ fu` / `じ ji` / `ぢ ji` / `づ zu` | `つき` → `tsuki` |
| 拗音 | `しゃ sha` / `ちゃ cha` / `じゃ ja` / `きょ kyo` ほか | `しゃしん` → `shashin` |
| 長音 | `おう`/`おお` → `ō`、`うう` → `ū`、`ああ` → `ā`、`ええ` → `ē` | `とうきょう` → `tōkyō` / `くう` → `kū` |
| 長音の例外 | **`いい` → `ii`**(JR `飯田橋 = Iidabashi`)、**`えい` → `ei`**(JR `京成 = Keisei`) | `ちいさい` → `chiisai` / `せんせい` → `sensei` |
| カタカナ長音符 | `ー` は直前の母音のマクロン | `コーヒー` → `kōhī` |
| 撥音 | `n`。**b・m・p の前は `m`** | `しんぶん` → `shimbun` / `さんぽ` → `sampo` |
| 撥音の切れ目 | 母音・や行の前は **アポストロフィ `'`** | `しんいち` → `shin'ichi` / `きんようび` → `kin'yōbi` |
| 促音 | 次の子音を重ねる。`ch` の前は `t` | `がっこう` → `gakkō` / `こっち` → `kotchi` |
| 促音(語末) | 落とす | `あっ` → `a` |
| 助詞 | `を` → **常に `o`**。`は` → `wa` / `へ` → `e` は**語として切り出せたときだけ**適用し、それ以外は字義どおり `ha` / `he` にして「要確認」印を付ける | `ほんを` → `hon o` |
| 定型句 | `こんにちは` → `konnichiwa` / `こんばんは` → `kombanwa` / `では` → `dewa` | — |
| 句読点 | `。`→`.` / `、`→`,` / `?`→`?` / `!`→`!` / `…`→`...` / `「」`→削除。読点の後ろに半角スペース 1 つ | — |
| 大文字化 | 行頭と `.` `?` `!` の直後の語だけ。**固有名詞は機械で判定しない** | `Takusan arukimashita ne.` |

**`こんばんは` = `kombanwa` の理由**: architect の原案は `konbanwa` だったが、
これは同じ表の「b の前は `m`」に反する。規則の一貫性を優先して `kombanwa` に直した
(`さんぽ` → `sampo` と同じ扱い)。

**アポストロフィにする理由(基準から意図的に外す唯一の点)**: 鉄道掲示基準規程は撥音の切れ目に
**ハイフン**を使う(`Shin-Ōkubo`)。しかしこれは複合固有名詞の**構成要素を切る**ための表記で、
`きんようび` のような一般語には合わない(`kin-yōbi` は「金」と「曜日」を別語に見せる)。
学習教材で一般的な修正ヘボン式のアポストロフィを採る。

### 2. `src/content/romaji.ts` — 第 1 層: `kanaToRomaji()`

```ts
kanaToRomaji(kana: string): string
```

かな 1 語をヘボン式にする。**スペースを入れない / 大文字化しない**。`Reading.romaji`
(`くう` → `kū`)にそのまま使える単位。変換できない文字は**そのまま残す**
(後段の `checkRomaji` が error として拾えるようにするため、握り潰さない)。

### 3. `src/content/romaji.ts` — 第 2 層: `segmentsToRomajiDraft()`

```ts
segmentsToRomajiDraft(segments: LineSegment[]): { draft: string; checks: RomajiCheck[] }
```

語の切り方は次の 3 段階で、**どれも「完璧」を狙わない**。

1. **語の結合(前プラン (b) の限定採用)**: 読みを持つセグメントは、直後のかなセグメントと 1 語にする。
   それ以外のセグメント境界は語境界(半角スペース)にする
2. **末尾語の切り出し(閉じた表のみ)**: 語の末尾から、長い順に貪欲に剥がす
   - どのセグメントでも剥がす: `ございます` `ございました` `でしょう` `ですか` `ですね` `でした` `です`
   - **読みを持つセグメントの直後のかなセグメント**でだけ剥がす 1 文字: `は へ を が に で と も ね よ か`
     (直後が句読点か語末のときのみ。剥がせた `は`/`へ` はここで `wa`/`e` に変える)
3. **長音はセグメント境界を越えない**: `思(おも)+う` は `omou`(`omō` にしない)。
   促音・撥音は語内の連結として扱う(`言(い)+って` → `itte`)。
   **これは今回いちばん効く設計判断**で、`おう` の長音か動詞語尾かという最大の曖昧さの多くが、
   既にある `segments` の構造だけで解ける

**かなだけのセグメントは分割しない。** `なに` を `na ni` と誤分割しないため。

`checks` は「要確認」印で、次の 3 種だけ:
- `particle`: 剥がせなかった `は`/`へ` が本文に残っている
- `proper-noun`: `japanese` に `ミア` / `空` が含まれる
- `unconverted`: 出力にラテン文字・記号以外が残った

## 実装後の記録(2026-08-28)

### プランの記述で誤っていた / 変えたもの

- **`こんばんは` の例外表。** architect の原案は `konbanwa` だったが、同じ表の
  「b の前の撥音は `m`」に反する自己矛盾だった。`kombanwa` に直した
  (`さんぽ` → `sampo` / `しんぶん` → `shimbun` と同じ扱い)。レビューでも妥当と確認された
- **`SUFFIX_WORDS` から `ですか` / `ですね` を落とした。** プランは両方を挙げていたが、
  長い順に貪欲に剥がすと `なんにんですか` が `nannin desuka` になってしまう。
  1文字の `か` / `ね` を先に剥がしてから `です` を剥がす形にすると
  `nannin desu ka` になり、こちらが正しい
- **`SUFFIX_WORDS` に `だった`、`SUFFIX_PARTICLES` に `ねえ` / `なあ` を足した。**
  会話文集 #1 で試したところ `たびだったねえ` が `tabidattanē` になったため。
  プランが「例外表を育てる」と想定していた範囲の調整

### レビュー指摘への対応

`reviewer` の判定は**要修正**。受け入れ条件は全項目満たしていたが、
条件が触れていない領域に、次のコンテンツ投入で確実に踏む欠陥が4件あった。すべて直した。

1. **語中の全角句読点が変換されず、しかも検知網が両方すり抜けていた**(最重要)。
   `すみません、かばんが` → `Sumimasen、kabanga` が `pnpm run check` を通過していた。
   原因は、句読点を語の**末尾からしか**剥がしていなかったことと、
   `、` `。` `「` `…` `？` が Unicode 上 Script=Common で、
   `\p{Script=Hiragana|Katakana|Han}` にも `[぀-ヿ㐀-鿿]` にも掛からなかったこと。
   → 語中の記号を一括置換する処理を足し、**検知網を「許す文字を並べる」形に反転**した
   (`ALLOWED_IN_ROMAJI`)。否定形で書くと必ずこの穴が空く
2. **読みの末尾の促音が消えていた。** `一(いっ)+匹(ぴき)` → `Ipiki`。
   → 単位の末尾に残った促音を次の単位の頭に送る `carrySokuon()` を足した
3. **読みを持つセグメントが連続すると必ず語が割れていた。** `何(なん)+人(にん)` → `Nan nin`。
   `docs/content-spec.md` が「新出漢字は単独のセグメントに」と勧めるので必ず起きる形だった。
   → **連続する読みは1つの単位に畳んでから変換する**ようにした。
   これで熟語の長音も畳まれる(`今(きょ)+日(う)` → `Kyō`)。
   一方で読み→送り仮名の境界は畳まないままなので `思(おも)+う` は `omou` のまま
4. **プランにあった「直後が句読点か語末のときだけ助詞を剥がす」条件が未実装だった。**
   `子(こ)+ども+がいます` → `Kodo mo gaimasu`。
   → `isFinal` と末尾句読点の有無を見るようにした。あわせて
   **直前が撥音・促音なら助詞ではなく活用語尾とみなす**ガードを足した
   (`読(よ)+んで` を `yon de` と割らないため。て形・で形は頻出する)

修正の過程で助詞の判定条件を厳しくしすぎて `いえ+は` が `ieha` になる回帰を出したが、
テストが捕まえたのでその場で戻した。

### 再レビューでの指摘への対応

1回目の修正後に再レビューし、さらに4件の取りこぼしが出た。**いずれも会話文集の実在の行で発火し、
`check` も `確認` 印もすり抜ける「静かに間違う」種類**だったのですべて直した。

1. **促音が未変換文字を飛び越えて次の子音を重ねていた。**
   会話文集 #6「あっ、また棚の上にいる。」が `A, mmata ...` になっていた。
   → 変換表に無い文字に当たった時点で促音を捨てるようにした
2. **最終ユニットの前に付いた記号が、stem を飛び越えて語頭に貼られていた。**
   会話文集 #1 の3行目が `.ippikianatade` のように融合し、
   文の切れ目が消えて大文字化も効かなくなっていた。
   → 記号は「直前の語の終わり」として stem の後ろに置くようにした
3. **`を` が行末以外で剥がれなくなっていた**(1回目の修正4の副作用)。
   `何(なに)+を+学(まな)+...` が `Nanio mananderundai?` になっていた。
   `を` は現代語では助詞用法しかなく曖昧さが無いので、位置で絞る理由がない。
   → `を` だけは `allowParticles` を経由せず常に切り出すようにした
4. **`ALLOWED_IN_ROMAJI` が2ファイルに手書きでコピーされていた。**
   今回いちばん重要な設計判断(検知網を許可リスト形式に反転した)の実体なので、
   片方だけ直すと また穴が空く。
   → `src/content/romaji.ts` から export し `validate.ts` が import する形にした。
   あわせて `\s` が全角スペースを、`\p{Nd}` が全角数字を通していたので半角だけに絞った

なお指摘2の期待値は、レビューが `Ippiki. Anatade` としていたが、
`あなたで` の `で` は実際に助詞なので `Ippiki. Anata de` が正しい。テスト側をそちらに合わせた。

### 3回目のレビューでの指摘への対応

2回目の修正には回帰が無いことを確認したうえで、これまで見ていなかった領域から3件出た。

1. **三点リーダの連続が6点・7点になっていた。** `……` を1文字ずつ置き換えるため、
   `……分かった。` が `...... Wakatta.` になっていた。会話文集に該当が12行(第1章に3行)。
   ドットは許可リストを通るので `unconverted` 印も立たない。
   → `[…‥]+。?` を1つに畳む `normalizeEllipsis()` を足した。原稿の英訳も3点で書かれている
2. **撥音の直後の `を` が剥がれず `gohan'o` になっていた。**
   2回目の修正3で `allowParticles` は迂回したが、その下の撥音・促音ガードを迂回し忘れていた。
   `を` は活用語尾になり得ないので、このガードを当てる理由がない。
   → `particle !== 'を'` の条件下でだけガードを効かせるようにした
3. **手順書が「確認印が付いた行を直す」と書いていて、印の無い行は素通りしてよいと読めた。**
   レビューが第1章10文(26行)を実際に流したところ、**綴りは全行正しい一方、
   20行で語の切れ目の手直しが必要**だった。印は `は`/`へ` と固有名詞しか見ないので、
   `が`/`に`/`の` の融合には立たない。
   → `docs/content-spec.md` と `.claude/skills/add-content/SKILL.md` を
   「**下書きは全行を目で見る。印は特に危ないものを指すだけ**」に直し、
   **この道具は綴りの辞書引きであって、そのまま貼れる下書きではない**という位置づけを明記した

### レビューを3周した結果として分かったこと

**この変換器の価値は分かち書きではなく綴りの統一にある。** 3周を通じて、
`ō` / `shimbun` / `tsu` / `kin'yōbi` といった綴りは実データ全行で正しく出る一方、
語境界は第1章26行中20行で人が直す必要があることが実測で分かった。
