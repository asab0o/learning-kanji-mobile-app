# 実装プラン置き場

`/plan-feature <機能名>` が生成し、**開発者が承認したもの**だけがここに入る。
実装中はこのファイルが仕様の作業コピーになる。完了したら `## ステータス` を `完了` にする。

## テンプレート

```markdown
# プラン: <機能名>

作成日: YYYY-MM-DD
ステータス: 提案中 | 承認済み | 実装中 | 完了
要件定義書の対応箇所: <セクション番号>

## 目的
この機能が満たすユーザー体験を1〜2文で。

## スコープ外
今回やらないことを明示する。ここが曖昧だと実装が膨らむ。

## 変更するファイル
| ファイル | 新規/変更 | 内容 |
|---|---|---|

## データモデルの変更
なければ「なし」。あればマイグレーションの要否まで書く。

## 実装ステップ
1.
2.

## 受け入れ条件
- [ ] 検証可能な形で書く(「正しく動く」ではなく「Xを入力するとYになる」)
- [ ] レビュー担当はこのリストで合否を判定する

## テスト方針
どの純粋ロジックにユニットテストを書くか。UIは手動確認でよい範囲を明示する。

## リスク・未確定事項
```

## 受け入れ条件の書き方

`reviewer` サブエージェントはこのリストを判定基準に使うので、
**外から観測できる形**で書く。

- ✗ 「SRSが正しく動く」
- ✓ 「不正解を記録すると、その漢字のステージが1つ下がり、次回出題日が当日になる」
