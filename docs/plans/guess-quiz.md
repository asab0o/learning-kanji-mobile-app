# プラン: 推測クイズ「読めるかな?」

作成日: 2026-09-06
ステータス: 完了(2026-09-06)
要件定義書の対応箇所: 4.4 / 5.1-6(関連: 4.1-6, 3.3, 6.3, 7章)

## 要件との差分(2026-09-06 に5件すべて承認済み)

要件を実装に落とす前に、**要件の文面どおりには作れない/作らないほうがよい点が5つ**あった。
**開発者が5件すべてを承認済み。** 差分2 については「人によって易しい・難しいの基準が異なり、
日本語能力試験の順序どおりでないことを実感している」という理由で定義変更を了承。
差分4 は選択肢 A(セッション直後)を採用し、B(セッション中に割り込む)は採らない。

### 差分1. 要件4.4 の出題例(歩道・空気)は、そもそもデータ上作れない

要件4.4 は種明かしの例として `歩=walk + 道=road → sidewalk`、出題例として
`空(そら)→ 空気の空`を挙げていますが、**`道` も `気` も対象50字に入っていません**
(`src/content/index.ts` の漢字マスタで確認)。構成字の英語の意味は `KanjiEntry.meaning`
からしか引けないため、この2語は種明かしを組み立てられません。

対応案: **出題対象を「構成字がすべて対象50字に含まれる熟語」に限定する**。
実データを数えた結果は次のとおりです。

| 条件 | 語数 |
|---|---|
| `words` の異なり(surface 単位) | 123 |
| うち漢字2字以上の熟語 | 68 |
| うち構成字がすべて対象50字 | **25** |
| さらに第2段階の演出語を除く(差分3) | **19** |

母数は小さいですが、要件4.4 が求める「既習漢字から意味を推測する」体験自体は成立します。
増やすには content 側に構成字の英語グロスを持たせる必要があり、それは今回スコープ外。

### 差分2. 要件4.4 の「易しめ / 難しめ」は素直に読むと初日に成立しない

「学習直後=易しめ / 復習中=難しめ」を「易しめ=構成字が全部既習」と読むと、実データでは
**15字目(第2章の途中)を学ぶまで易しい問題が1問も存在しません**(学習順に既習を増やして
実測: 3字時点で0問、10字=第1章読了時点でも0問、15字でようやく2問)。
無料範囲だけの学習者は易しい問題に一度も当たりません。

対応案: 難易度を**時間軸で読み替える**。

- 学習直後(易しめ) = **その日に学んだ字を含む語**を優先する。今さっき絵と意味を見た字なので推測が効く
- 復習セッション後(難しめ) = **既習字を今日より前に学んでいる語**を優先する。要件4.4 の
  「記憶から引き出させる」に合致する

どちらも該当が無ければ、条件を落として出題可能な語から選ぶ。

### 差分3. 第2段階の演出語をクイズに出すと、最大の差別化がネタバレする

`reencounters` の演出語は8語(日曜日/水曜日/時間/休日/大学/学生/新聞/外国)。このうち
**6語が上記25語の候補と重なります**。クイズは「未習の単語」を出す仕様(4.4)なので、
放っておくと**演出回(#38 時間、#45 大学 など)に到達する前にクイズが先に読みと意味を
明かしてしまう**。要件3.3 が「最大の差別化」と明記した段階的再登場の驚きが消えます。

対応案: **`Reencounter.word` に載っている語はクイズの出題対象から一律で外す**
(要件には書かれていない制約なので明示して承認をもらう)。

### 差分4. 「SRS復習セッション**中**」ではなく「セッション**直後**」に出す提案

要件4.4 の表は「数日後(SRS復習セッション中)」としています。提案は**セッション終了画面
(`All reviews done.`)からの導線**です。

理由: 既存の `src/features/srs/session.ts` の冒頭コメントが「クイズはセッションの前後に
別画面として差し込む形にする。混ぜると『SRSに入れていない』ことをレビューで確認できなく
なる」と既に決めており、セッションのキュー・進捗(`answeredCount / total`)にクイズ問題を
混ぜると、絶対規則10 を満たしていることが外から検証しづらくなります。
9月上旬の機能凍結を踏まえた縮小案でもあります。

要件文面に忠実にするなら「セッションの n 問目の直後に割り込む」形になりますが、
**その場合は別プランにしたい**(セッション状態機械の変更を伴うため)。

### 差分5. 要件4.4「単漢字の別の読み」を単独の出題形式としては作らない

「空(そら)を既習 → 空気の空は?」という読みの出題は、差分1のとおり `空気` が作れないうえ、
**読みを問う出題は要件5.5 で「読みの入力式クイズ」が Deferred**、SRS も「意味の4択のみ」
(ADR-0007)で統一されています。クイズも**意味の4択1本**に統一し、読みは答え合わせの
種明かしで見せる形にします。

---

## 目的

学習直後と復習の直後に、**既習の漢字を含むまだ会話文で出会っていない熟語**を1問だけ出し、
意味を4択で推測させたうえで「この語は 人(person) + 間(space between) でできている」と
種明かしすることで、「漢字は意味の核である」という感覚をその場で体感させる。成績はつけない。

## スコープ外

今回やらないこと(削った案はここに残す)。

- **復習セッションの途中に割り込む出題**(差分4)。セッション終了後の導線のみ
- **1回に複数問出すモード**。1回の入場につき1問。連続で解くと「ご褒美」ではなく「課題」になる
- **正答率・連続日数・スコア・履歴画面**。`quiz_attempts` は「同じ問題を続けて出さない」
  ためだけに読む(`docs/data-model.md`)
- **クイズ結果の SRS への反映**(絶対規則10)。`review_events` には一切書かない
- **手書きの誤答選択肢・種明かし文を content に足すこと**。誤答は既存の `words` の意味から
  機械的に作る
- **対象50字の外の字を含む語の出題**(歩道・空気・小学校・毎日 など)。構成字の意味が無く
  種明かしが組めない
- **第2段階の演出語の出題**(差分3)
- **読みを問う出題形式**(差分5)
- **Today 画面(`src/app/index.tsx` / `today-view.tsx`)からのクイズ入口**。並行実装中の
  「漢字の樹」と競合しやすく、入口を増やすと「回せるモード」になってしまう
- **漢字の樹への反映・演出アニメーション**(要件4.6 ステップ3と同じ理由で `features/tree/` 側の担当)
- **クイズ専用の課金ゲート**(下記「実装ステップ」6で理由を書く)
- **`quiz_attempts` の列追加・マイグレーション**。既存スキーマのまま使う
- **オンボーディングでのクイズ紹介**

## データモデルの変更

**なし。マイグレーション不要。**

`quiz_attempts` は `src/db/schema.ts` に既にあり、`0000_lethal_alice.sql` で作成済み。
今回はそれを**初めて使う**だけ。

- `item_key` の形式を **`word:<surface>`**(例 `word:人間`)に確定する。`words` の行 ID を
  使わないのは、同じ語が2つの漢字の樹に別 ID で重複して入っているため(`時間` は 時 と 間 の
  両方に存在)。行 ID をキーにすると同じ語が2回出せてしまい、この表を持つ唯一の目的
  (同じ問題を続けて出さない)が果たせない
- 書くのは回答時の1行だけ。`result` は入れるが**読むのは `item_key` だけ**。
  正誤は集計にも表示にも使わない

## 実装ステップ

1. **`src/db` に読み書きを足す。** `src/db/queries/quiz-attempts.ts`
   (`insertQuizAttempt` / `listRecentQuizAttempts(limit)`)を新規追加し、`src/db/index.ts`
   から公開する。**UPDATE / DELETE は書かない。**

   **`listWords()` は書かない。**漢字の樹のブランチが既に同名同型で追加しており
   (2026-09-06 に `git diff` で確認)、ここで足すと確実に衝突する。
   **樹が main にマージされてから着手すること。**

2. **`src/features/quiz/selection.ts`(純粋)。** 入力はすべて呼び出し側から受け取り、
   `@/db` にも `@/features/srs` にも触れない。

   ```
   pickQuizItem({
     words,                 // Word[]  (@/content/types)
     kanji,                 // KanjiEntry[]
     reencounterWords,      // string[] 第2段階の演出語(差分3)
     learned,               // { kanjiId, completedAt }[]  lesson_events 由来
     completedSentenceIds,  // string[] lesson_events 由来
     recentItemKeys,        // string[] quiz_attempts 由来(新しい順)
     slot,                  // 'lesson' | 'review'
     now, rng
   }) => QuizItem | null
   ```

   出題可否のふるい(この順に、テストもこの順で書く)。

   1. 漢字2字以上
   2. **構成字がすべて漢字マスタにある**(種明かしを組めることの保証。差分1)
   3. **構成字の1つ以上が既習**(`learned` にある。要件4.4「既習漢字を含む」)
   4. **まだ出会っていない語**(`encounteredInSentenceId` が null、または
      `completedSentenceIds` に無い。要件4.4「未習の単語」)
   5. **第2段階の演出語を含まない**(差分3。完全一致ではなく**部分一致**で外す。
      レビュー指摘で広げた。理由は「リスク・未確定事項」)
   6. **`recentItemKeys` の先頭 N 件(N=10)に無い**。全滅したらこの条件だけ落とす
      (枯渇しても黙って止まらないようにする)
   7. 残りから `slot` に応じて優先順位を付ける(差分2)。同点は `rng` で選ぶ

   `QuizItem` は `{ itemKey, surface, kana, meaning, components: { character, meaning, learned }[] }`。
   **画面が判断を持たなくていい形まで詰めて渡す。**

3. **`src/features/quiz/distractors.ts`(純粋)。** 要件4.4「片方の漢字だけ合っている
   紛らわしい選択肢」を、**手書きせずに既存データから作る**。

   - 第1候補: **正解語と漢字をちょうど1字だけ共有する別の語**の意味
     (例 `花火` → `火山` volcano / `花見` flower viewing / `火曜日` Tuesday)
   - 不足したら共有0字の語の意味で埋める
   - 正解と同じ意味・重複する意味は除く。最後に `rng` でシャッフル
   - 実データで供給量を確認済み: 候補25語のうち最少が `新聞`(共有1字の語が2件)で、
     ここだけ1件を無関係な語で埋める。他は3件以上ある

   **`src/features/srs/choices.ts` は再利用しないし、共通化もしない。** 同ファイルの冒頭
   コメントが「あちらは推測の質を上げるもの、こちらは意味を思い出せるかを見るもの。
   **共通化しない**」と既に宣言している。入力(片方は `KanjiEntry`、片方は `Word[]` の
   関係グラフ)も、誤答の選び方(品詞の形をそろえる vs 構成字を1字だけ共有させる)も別物で、
   共通化すると両方に効く分岐が増える。**共有するのは Fisher-Yates シャッフルの十数行だけで、
   それは重複を許す**(共通ユーティリティに切り出すと、rng 注入の契約を2機能で握り合うことになる)。

4. **`src/features/quiz/components/quiz-view.tsx`(表示専用)。** 要件4.4 の2段構え。

   - **第1段: 語を漢字だけで大きく出す。**ふりがなも英訳も出さない。
     `Can you guess what this means?` と `Show choices` ボタンだけ。
     **押すまで4択を出さない**(要件4.4-1)
   - **第2段: 4択。**選ぶと正誤を色で示す(既存 `review-session-view.tsx` と同じ
     `theme.positive` / `theme.negative`)
   - **第3段: 種明かし(ここが最重要)。**読み(**かなのみ。ローマ字は出さない** —
     2026-09-06 決定。理由は下の「リスク・未確定事項」)と、構成字を1行ずつ:
     ```
     人  person
     間  space between
     → human being
     ```
   - CTA は `Back to today` の1つだけ。**スコア・正答率・連続日数・進捗(n/m)を一切出さない。**
     「ご褒美体験であり成績ではない」(要件4.4)を UI の事実として表す
   - 出題できる語が無いときは `Nothing new to guess right now.` と Back CTA だけを出す
   - 文言はすべて英語(絶対規則7)、色はすべて `theme.*` トークン経由(絶対規則1)

5. **`src/app/quiz.tsx`。** `listWords` / `listKanji` / `listSentences`(演出語の抽出用)/
   `listLessonEvents` / `listRecentQuizAttempts` を**遅延初期化で1回だけ**読み、
   `pickQuizItem` に渡す。回答時に `recordQuizAttempt` を呼ぶ。

   **`setState` の updater function の中で DB に書かない。** `src/app/review.tsx` の長い
   コメントにある通り、React Compiler 有効下で updater は複数回呼ばれうる。ここで踏むと
   `quiz_attempts` に二重に入り、「同じ問題を続けて出さない」の窓が静かにずれる。

6. **入口を2つ繋ぐ。**
   - `src/app/kanji/[id].tsx`: `completeLesson()` の後に `router.replace('/quiz?slot=lesson')`。
     クイズを閉じるときに従来と同じ `canDismiss() ? dismissAll() : replace('/')` で Today に戻す
   - `src/app/review.tsx`: `ReviewSessionView` に `onQuiz` を渡し、`All reviews done.` の下に
     `Bonus: guess a word` を出す(文言は実機確認で変更。理由は「実装後の記録」)

   **課金ゲートは掛けない。** 出題語は「既習字を含む語」に限られ、既習字は課金ゲート済みの
   学習フロー(`gateSentences`)を通ってしか増えないため、**未購読者の出題範囲は構造的に
   第1章の10字由来に閉じます**。クイズは会話文を1行も表示しないので、有料コンテンツ
   (会話文と学習フロー)は漏れません。難しめの問題では未習の相方の字の意味が1語見えますが、
   それは要件4.4 が明示的に許している出題形態(「既習1字＋未習1字の熟語」)であり、
   有料の中身ではありません。

7. `pnpm run check` を通し、iOS シミュレータで受け入れ条件の手動項目を確認する。

## 受け入れ条件

- [ ] 第1章1文目(`人`)を学び終えると続けてクイズ画面が開き、**`人` を含む語**(`人間` か

      (`人間` なら `person` / `three people` / `foreigner` / `space between` のいずれか)
- [ ] 選択後に、読み(かな)と構成字の内訳(`人 person` / `間 space between` /
      `→ human being`)が表示される

- [ ] **不正解を選んで Today に戻っても、`Reviews` の `n due` が回答前と変わらない。**

## テスト方針

主戦場は純粋ロジック2つ(`architecture.md` のテスト方針に一致)。

**`selection.test.ts`**(フィクスチャで書く。実データに依存しない)

- 構成字がマスタに無い語は選ばれない
- 既習字を1字も含まない語は選ばれない
- 完了済みの会話文で出会った語は選ばれない / 未完了の回で出会う語は選ばれる
- 第2段階の演出語は、他に候補が無くても選ばれない(返り値は `null`)
- `recentItemKeys` にある語は選ばれない。全候補が recent のときは条件を落として1問返す
- `slot: 'lesson'` は当日学んだ字を含む語を優先し、`slot: 'review'` は既習日が今日より前の語を優先する
- 候補が無ければ `null` を返す
- `rng` を固定すると同じ入力から同じ語が返る

**`distractors.test.ts`**

- 常に4件、重複なし、正解の意味をちょうど1つ含む
- 共有1字の語が3件以上あるとき、誤答3件すべてが共有1字の語の意味になる
- 共有1字の語が2件しかないとき(`新聞` 相当のフィクスチャ)、不足分を共有0字の語で埋めて4件になる
- 正解と同じ意味を持つ別の語は誤答に入らない
- `rng` 固定で並びが決定的

**`boundaries.test.ts`**

- `src/features/quiz/` 配下のソースを読み、`@/features/srs` / `review_events` / `recordReview`
  の文字列が含まれないことを assert する(絶対規則10 が後から破られたら CI で落ちる)

**手動確認(シミュレータ)**: 2段構えの見た目、種明かしの改行、
`replace` → `dismissAll` の戻り先、復習終了からの導線。

   プランの「変更するファイル」表を書いた時点では未マージだった

### レビューで直したこと

- **`boundaries.test.ts` の禁止語が空振りしていた。** `review_events`(スネークケース)は

### 実機確認で変えたこと

- **CTA を `Can you read this?` → `Bonus: guess a word` に変えた(2段階で決めた)。**
  1. `read` を捨てたのは、このアプリで "reading" が Kun / On バッジと「読みが変わった」
     演出の指す**かなの読み**であり、学習者に「何と発音するか」と読めるため。
     クイズが訊くのは意味で、読みは答え合わせで初めて出る
  2. さらに `Bonus:` を冠したのは、**この CTA が意味4択の復習を解き終えた直後に出る**から。
     `Can you guess this word?` だと同じ問いがもう1問続くように見え、ご褒美ではなく
     ノルマになる(要件定義書 4.4「ご褒美体験であり成績ではない」)

  要件の機能名「読めるかな?」は日本語の**内部名**であって、UI 文言(英語。絶対規則7)は
  直訳に縛られない。

- **`slot: 'lesson'` に「たった今学んだ字」の段を足した(`focusKanjiId`)。**
  実機で `小` を学び終えた直後に `人間` が出て、開発者が「唐突」と指摘した。原因は
  寄せ方が**その日に学んだ字**までしか見ていなかったこと。1日3字学ぶので、`小` の回でも
  同じ日に学んだ `人` の語が正当に選ばれてしまう。要件4.4 が学習直後の枠を
  「**今さっき絵と意味を見た字**なので推測が効く」と説明している意図から外れていた。
  `kanji/[id].tsx` が `&kanji=<id>` を渡し、`preferForSlot` の1段目で
  「その字を含む語」を最優先にする(無ければ従来どおり当日の字 → 候補全体に落ちる)。
  - **頻度(毎レッスン出る)はそのまま。** 出題が直前の字に紐づいた結果、
    「さっきの字の応用」として読めるようになったため。1日1回に絞る案は採らなかった

### 見つけたがやらなかったこと(スコープ外)

- **`words` の同じ `surface` の行で `kana` / `meaning` が一致することを、誰も検査していない。**
  `words` は漢字の樹の葉なので2字の熟語は両方の字の樹に1行ずつ入る(重複は現在7語)。
  クイズは出題時に `rows[0]` から読みと意味を取るが、`listWords()` に `ORDER BY` が無く
  **どちらが先頭に来るかは SQLite 任せ**。2行が食い違うと、実行のたびに表示が揺れる。
  2026-09-06 時点では**7語すべて一致していて実害なし**。
  拾うなら `src/content/validate.ts` に不変条件を1つ足す(コンテンツ側の話なので別タスク)。
