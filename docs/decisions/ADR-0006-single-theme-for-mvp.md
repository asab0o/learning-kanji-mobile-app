# ADR-0006: MVP のテーマを桜1種に絞る(追加できる形は残す)

日付: 2026-08-29
ステータス: 採用

## 背景

要件定義書 5.1 の Must have #9 は「テーマ切り替え(3種)」= ノーマル / 桜 / 東京の夜景 と
定めていた。桜だけが ADR-0004 で確定しており、残り2種は「デザイン保留」のまま
2週間以上動いていない。

8/29 時点の残作業を並べたところ、Shipaton の期限(9/30)と要件定義書 8章の
「9月上旬を目安に機能凍結」に対し、Must have のうち **9項目が未着手**で、
そこに漢字イラスト50枚とストア登録作業が乗る。CLAUDE.md の
「迷ったらスコープを削って出す」に従い、削る先を決める必要があった。

## 決定

**MVP に積むテーマは桜1種のみとする。** ノーマル / 東京の夜景は v2 以降に送る。
テーマ切り替えUIも作らない(切り替える先が無いため)。

ただし**テーマを後から足せる形は壊さない**。要件定義書 5.3 の制約に、
壊してはいけないものを列挙した。

## 理由

### 1. 削っても差別化が減らない

第2段階の演出・推測クイズ・漢字の樹は「漢字は意味の核である」という
仮説(要件3.1)に直結するが、**テーマは体験の質に効くだけで、仮説の検証には効かない**。
Must have の中で、削っても検証したいことが検証できなくなるものが他に無い。

### 2. 削減量が大きい

1種あたり **配色11トークンの設計 + 背景画像1枚の生成 + 視認性の確認**が要る。
特に「東京の夜景」は 5.3 が自ら注意しているとおり暗色テーマで、
文字色・枝の色(kunBranch / onBranch)・背景装飾の重なりを全画面で見直す必要がある。
2種で1〜2日、視認性の手戻りを含めるともっと膨らむ。

### 3. **削っても、戻すのが安い状態が既に出来ている**

実装を確認したところ、テーマ層は最初から追加前提で書かれていた。

| 仕組み | 効果 |
|---|---|
| `ThemeId` が union 型 | 増やすと `themes` が型エラーになる |
| `themes: Record<ThemeId, Theme>` | テーマを足して定義を書き忘れると型で止まる |
| `themes.test.ts`「全テーマが同じキー集合を持つ」 | 片方にしかないトークンを作れない |
| `user_settings.theme_id` 列(`src/db/schema.ts`) | 選択状態の置き場が既にある。マイグレーション不要 |
| `ThemeProvider` の `themeId` プロパティ | Provider は選択状態を持たない。渡す側を足すだけ |
| 色は全て `theme.*` 経由(絶対規則1) | 画面側の色指定を洗い直す必要が無い |

**足すときに要るのは、配色オブジェクト1つと背景画像1枚と切替UIだけ。**
今回の決定は「作らない」であって「作れなくする」ではない。

## 却下した選択肢

- **3種のまま進める**: 期限に対して他の Must have が9項目未着手。テーマを残すために
  クイズや樹の質を落とすのは、削る順序として逆
- **ノーマルを足して2種にする**(暗色の夜景だけ落とす): 一見安いが、切り替えUI・
  設定画面の項目・切り替え時の再描画の確認が発生し、「1種 → 2種」の段差が
  「2種 → 3種」より大きい。**切替UIごと落とせるのが1種の価値**
- **`ThemeId` を `'sakura'` 単一リテラルに固定して型を単純にする**: 型は簡単になるが、
  戻すコストを自分で上げる。テーマを足す動機は「余裕が出たら」であって
  「もう足さない」ではない

## 結果として受け入れるトレードオフ

**ストアのスクリーンショットと紹介文で「テーマ切り替え」を売りにできない。**
桜1種は世界観としては強いが、「自分好みにできる」訴求は使えなくなる。

また、**暗色テーマでの視認性が MVP では一度も検証されない**。
5.3 が挙げている懸念(濃色背景で本文が読めなくなる、樹の枝の色が沈む)は
夜景テーマを作る回に初めて現れる。トークンは全テーマ同じキーを持つので
機械的な漏れは起きないが、**色の選び直しは発生する前提で見積もること**。
